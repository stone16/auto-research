Logic notes
  • Overview shows only depth 0. Top-level Objectives are the only things on this screen. Descendants are invisible here on purpose. You are making priority decisions at the Objective level, not execution decisions at the leaf level.
  • Each card answers one question: "should I pay attention to this now?" That is why every card has a Next attention field driven by the State Layer's next_step computation. The overview is prescriptive, not just descriptive.
  • No hierarchy is drawn at this level. Multiple top-level Objectives are parallel, not siblings under a virtual root. We removed the virtual-root idea; drawing one would misrepresent the workspace structure.
  • Rollup state leaks up from descendants. The "Build OKR Dashboard" card shows rollup 38% and (!) and (?) flags even though its own progress is 42% and its own state is fine. The blockers and review flags live on descendants; the overview surfaces them so you see "this Objective has attention needs" without drilling in.
  • "Open tree →" is the only navigation action on this card. Everything else (edit intent, edit acceptance, trigger Run, approve) happens in focused views (Objective tree → Node panel).
What this view does NOT show
  • Sub-goal details. You only see the count.
  • Individual Run status. You only see "1 in-flight" aggregated.
  • Acceptance criteria. You only see the aggregated progress percentage.
  • Structural hierarchy between Objectives. There intentionally is none to show.

The same 8 Nodes rendered with one single root ("Build OKR Dashboard"). Hierarchy is unambiguous: parent sits above children, children hang off a horizontal bar under the parent.
Why this view
  • Visual metaphor matches the word. When you say "we're drawing a tree" you now literally draw a tree. No translation between mental model and visual model.
  • Parent-child direction is unambiguous. Up is parent, down is child. No indent counting, no rail colors, no column numbers. Spatial relationship IS semantic relationship.
  • Depth equals vertical row. Every Node at depth N sits at the same horizontal plane. Siblings line up naturally.
  • Single-root only. This view is entered by clicking ONE Objective in the Workspace Overview. It draws that Objective's tree, nothing else. Multiple parallel Objectives are handled by going back to Overview and clicking a different one — they never share a tree.
  • Breadcrumb anchors the focus. The "← Workspace overview / Build OKR Dashboard" strip tells the user exactly where they are and how to get back.
Honest tradeoffs
  • Breadth is the real limit, not depth. A node with 12 children at one level pushes the tree horizontally very wide. Mitigations: compact cards, collapse rarely-touched branches by default, horizontal scroll inside .tree-td-wrap (which is already enabled).
  • Card size is constrained (~210-240px wide) so the tree doesn't explode. Fits intent + 1 meta line + 1 progress bar + 1 badge row. For anything more, click the card → Layer 1 Panel.
  • Deep asymmetric trees look lopsided. If one branch is depth 5 and its siblings are leaves, the layout has big empty columns. This is correct — empty space is honest about "nothing happening here" — but it can feel sparse.
  • For "100+ Nodes fully expanded" use cases this still overwhelms, just like any visualization. The fix is progressive collapse (click a card to collapse its subtree), not a different layout.

Design principles (action-first)
  • Actions are the dominant element. The big colored buttons ("Approve" / "Reject" / "Trigger Run") are the first thing the user sees after the intent. Data exists to support action decisions, not as an end in itself.
  • "Tell agent" is always present. The user can type a free-form instruction to the agent at any time. This is the primary human-agent interaction surface. It replaces the old "trigger Run with angle" pattern with a natural language input.
  • Notification banner appears only when the system has something to say. In the calm state (Example B), there is no banner at all. The panel feels empty, which is the correct feeling — it means "nothing needs your attention, the agent is working."
  • All data sections are collapsed by default. The one-line summary on each collapsed row (e.g. "3 assertions PASS · 2 metrics MET") gives enough context without expanding. Power users expand; regular users never need to.
  • Secondary actions are text links, not buttons. "Edit goal", "Edit acceptance", etc. are de-emphasized because they are infrequent contract-change operations, not the primary workflow.
  • The calm footer ("All quiet. Agent is working.") is intentional UX. It tells the user "you don't need to do anything right now" and gives permission to walk away. This is the opposite of a dashboard that always screams for attention.
What changed from the old dense panel
  • Before: 10 sections all expanded, acceptance details fully rendered, 10+ action buttons visible, information overload.
  • After: intent + progress bar + notification (if any) + 2-3 primary action buttons + agent chat input + 5 collapsed data rows. The panel is 60% shorter.
  • The rule: if the user has to read more than 3 seconds to figure out what to do next, the panel failed. The notification banner + primary actions should answer that question instantly.
References: Foundations §13 (agent/human default split) · §14 (progressive disclosure). Task #6 (UX philosophy). Key insight from this iteration: Level 2 is the ACTION surface, not the DATA surface. Data is on-demand, actions are always-visible.

Three phase invariants
  1. Freeze is one-way. Draft → Active legal. Active → Draft illegal. Never.
  2. Complete is terminal. No transitions out except fork-to-new-Node. "Oops we weren't done" → create a new child to capture the gap, never revert.
  3. In-Review is an execution barrier. No new Run dispatches allowed while a Node is In-Review. This is what makes human review align with a frozen artifact snapshot rather than a moving target.
Logic notes
  • Phase is not decoration. It's an execution gate. Dispatching a research_iteration Run to a Draft Node is a data-layer error, not a policy error.
  • Born-structured children skip Draft. When a parent in Active spawns children via its acceptance, those children enter Active directly with acceptance inherited from the parent.
  • Complete and Archived are both terminal but distinct. Complete = "did it." Archived = "stopped doing it." Failure is an archived_reason, not a separate phase.
  • In-Review blocks the execution layer, not the editor. You can still add human notes, drill into past Runs, leave feedback. You just can't mutate contract or start new work until the review resolves.

View 6 · Node lifecycle

Freeze co-authoring session

A conversational schema builder, not a form. Agent proposes each item with reasoning. User can edit, reject, append, skip, pause, or reset at any point. Session state persists across pauses.

Logic notes
  • Every proposal carries reasoning that cites specific doc sections. The agent cannot propose in the dark; it must tie each item to evidence (prose, parent context, foundations invariants). This is the same judge-with-evidence pattern used in production LLM eval.
  • Six user interruption actions are first-class: Accept / Edit / Reject / Append own / Skip layer / Pause / Reset. None of these is an edge case.
  • Pause persists partial state. On resume, the agent does a fresh read of Node docs plus the partial schema. Already-confirmed items are not reopened. This keeps the session idempotent across time.
  • Sessions progress layer by layer: assertions → metrics → rubric → done_when. User can "skip this layer" if the Node doesn't need that dimension.
  • This is a UX commitment, not a polish detail. Without co-authoring, the freeze becomes a giant form, users avoid it, and the whole structured-acceptance pillar collapses.

Logic notes
  • Scratchpads are physically disjoint directories. No git conflicts are possible because sub-Runs never touch each other's files.
  • Returns are typed records, not prose blobs. The primary agent reasons over {findings, concerns, confidence, needs_human_review}, a fixed 4-field schema. It never has to parse natural language.
  • Synthesis is the parent agent's reasoning, not an algorithm. There is no merge function. The agent writes a synthesis reasoning log that describes what it kept, merged, discarded, and why.
  • Escalation is agent-driven. sub-Run-C's needs_human_review bubbled up because Run-P-2's agent chose to promote it. Had Run-P-2's agent decided the concern was already handled, it could have suppressed the flag. No structural promotion rule.
  • Sub-Runs are invisible by default. Users never see A/B/C unless they explicitly drill into Run-P-2. This protects the "user only faces Node tree" commitment.

  • Contract edits do NOT block. User can edit freely even with in-flight Runs. This preserves "human always in control."
  • The Run's agent decides the outcome, not the system. Continue / abort / restart is reasoning, not a rule table. Agent is closest to the actual state and most competent to judge.
  • Reconcile applies to all contract fields, not just acceptance. Editing local_policy triggers the same protocol. This generalization is the direct consequence of Task #10's lock.
  • Every reconcile decision is an audit_trail event. Three months later, opening this Run shows what contract it was dispatched against, what the new contract was, and why the agent continued / aborted / restarted.
  • No silent version forks. The Node keeps its single identity; it does not split into "v1 branch" and "v2 branch." Soft-fork was considered and rejected because it turns the OKR tree into a version tree.
